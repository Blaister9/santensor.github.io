01 / AI & MACHINE LEARNING

Intelligence with a human checkpoint.

Experimental prototype

Architecture at a glance

  1. Request
  2. Rules
  3. Mock API
  4. Human
  5. Record
Problem
An incoming request needs structure and a responsible decision.
Context & constraints
Synthetic requests only. No trained model or production data is used in the public lab.
Architectural decisions
Separate extraction, policy, tool access and approval. Uncertainty is visible and cannot bypass review.
Implementation
A deterministic state machine with six stages, an inspectable event trace and a recoverable mock service failure.
Verification
Unit tests cover guardrails; browser tests exercise approvals, ambiguity, failures and keyboard inspection.
What this demonstrates
An orchestration contract that can be inspected before adding a model. No inference-quality or business-impact claim.
What I would change next
Add a bounded evaluation dataset and a secure model adapter after budget and backend approval.
02 / SOFTWARE & SYSTEMS

English practice. Private by design.

Experimental prototype

Architecture at a glance

  1. Interface
  2. Server controls
  3. Voice session
  4. Consented history
Problem
Technical interview practice needs relevant questions and useful feedback.
Context & constraints
The existing private trainer uses job descriptions, voice sessions and optional history. Audio-device acceptance remains a separate test.
Architectural decisions
Keep credentials server-side, enforce session limits and separate the interface language from spoken English.
Implementation
Next.js, WebRTC and PostgreSQL, with explicit persistence consent and server-side session controls.
Verification
The repository contains authentication, limits and voice-lifecycle tests. Browser mocks do not prove physical Android audio.
What this demonstrates
A working private application architecture. No claim of certified language proficiency or hiring outcomes.
What I would change next
Complete a physical Samsung session and validate evaluation usefulness with consented user feedback.
03 / ENTERPRISE AUTOMATION

From request to accountable handoff.

Reconstructed case

Architecture at a glance

  1. Intake
  2. Directory
  3. Recovery
  4. Review
  5. Assignment
Problem
Requests crossing tools can lose context and ownership.
Context & constraints
A fictional directory and request queue reconstruct a common enterprise workflow. No institution or client is represented.
Architectural decisions
Treat policy as explicit rules and tool failures as recoverable states. Keep human ownership visible.
Implementation
The lab reconstructs intake, directory lookup, approval and assignment using synthetic data.
Verification
Scenarios demonstrate an accepted request, manual triage and a service outage without making external changes.
What this demonstrates
Traceable control flow and integration boundaries. No production time-saving or revenue metrics are asserted.
What I would change next
Validate real API contracts, retries and operational ownership in an authorized integration environment.
